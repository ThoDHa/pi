# Agent Viewer

Ambient observation surfaces for subagent dispatches. This is a
standalone extension: it lives in its own directory under
`extensions/`, loads via pi's auto-discovery with zero `settings.json`
edits, and owns everything user-facing about dispatch observation —
the dispatch strip, the navigator view, their hotkey registration,
and the task-label heuristic.

The extension owns no dispatch state. The subagent extension owns
dispatch execution and publishes live state into the shared dispatch
state this extension reads (`extensions/subagent/registry.ts`,
converged on `globalThis`, since pi evaluates each extension's modules
in a fresh instance). Both extensions must be present; with no
dispatch in flight the strip shows its "No active dispatches"
placeholder.

## Dispatch Strip

The extension registers a global hotkey (default `alt+s`) that toggles an ambient strip widget above the editor. The strip is hidden until the first toggle and hidden again on the next one. While visible it renders, refreshed twice a second:

- One header line per dispatch, labeled with the dispatch's task label and mode
- One line per live agent: status glyph (⏳ running, ✓ done, ✗ failed), agent name, most recent streamed activity (tool call or text snippet), and elapsed duration. Blocking parallel agents get their line when the dispatch's concurrency slot picks them up, so agents queued beyond the cap add no line and each duration measures run time rather than queue time (the same lazy publication detached uses for its steps).
- Finished rounds collapsed to a single summary line per round (`✓ round 1 · 3/3 done · 2m`)
- Detached jobs appear alongside blocking dispatches, one line per started per-slot agent node carrying that node's status glyph, streamed activity, and duration (steps that have not started yet add no line); the one-line-per-agent-name rendering keyed off `job.status` remains only as a mixed-version defense for snapshots published before the per-agent wiring
- Settled dispatches (every task and job with nothing running) collapse to a single Completed
  summary line (✓ Completed · 3 dispatches, the mixed glyph ◐ when some failed), so finished work
  never crowds live content out of the budget; with nothing live the strip shows that one line
  rather than the no-dispatch placeholder
- A hint line naming the navigator key, always last

The strip owns its own line budget (12 lines): live tasks render before the single Completed line,
and content that does not fit, the Completed line included, is summarized as a `+N more` line above
the hint, so finished work never crowds live content out of the budget and the terminal never
truncates the widget.

## Navigator

A second hotkey (default `alt+n`) opens the navigator: a view hosted as a full-width, top-anchored overlay (`ctx.ui.custom` with `overlay: true`, anchored `top-center` at 100% width and full terminal height). While the view is open it is effectively full screen: on terminals of three rows and up it renders exactly the terminal's height every frame (a header line, the pane body padded to the full body budget, a hints line), so the frame's size never changes with the selected agent or its content length, and it holds the keyboard focus while the editor keeps its draft text untouched beneath. On a one- or two-row terminal the body budget's one-row floor exceeds the space left under the frame lines and the overlay's maxHeight truncates the frame instead. Width has the same degeneracy floor: the pane body needs 59 columns (the tree and detail panes' minimum widths plus the gap between them), so below 59 columns the frame-level cut trims the composed body with its own plain "..." ellipsis instead of the pane-aware one, and below roughly 29 columns the focused row's cursor marker can be lost, the overlay itself being degenerate at that width. Escape and a second press of the open key close the view: the overlay hides and focus returns to the editor with its draft text (no second dialog stacks). The view re-reads the shared dispatch state ~3× a second, the same polling pattern the strip uses.

- **Left tree pane:** one row per dispatch task (labeled by the same heuristic as the strip), expanding to its dispatch rounds and their agents. A row longer than the pane's width share ends in an ellipsis instead of being silently cut, so a truncated label is visible as one, and the row keeps its single line (the full assignment lives in the detail pane). Completed rounds render as a single summary glyph line; the live round auto-expands. Detached jobs render as task nodes with their started agents directly beneath, each keyed off its own node status (snapshots published before the per-agent wiring fall back to `agentNames` children keyed off `job.status`). Selecting the Completed umbrella summarizes its settled dispatches in the detail pane, one line each; expanding it reveals their tasks, rounds, and agents with every detail affordance, including t on finished agents, unchanged.
- **Ordering:** live tasks lead the tree and every settled dispatch (registry task or detached job alike) collapses under one Completed umbrella row beneath them, defaulting collapsed and expanded with →, so active work stays at the top as older dispatches settle. Inside a task, rounds keep their chronological order; under an expanded umbrella the settled tasks keep their stable insertion order.
- **Right detail pane:** for a selected agent, a status header (status, model, cwd, context tokens, step for chain agents, duration) plus its streamed activity — timestamped lines for child thinking (dim, `…`-prefixed, so thought reads as thought), assistant text snippets, and tool calls with their arguments — its full-text thinking section (see below), the usage summary, and the final result when settled. For a task selection, the pane also carries the assignment itself: below the header, a `prompt` section renders the job's full source text one line per source line (blank lines kept as zero-width spaces), scrollable with the pane's paging keys and stable across polls; a registry task shows its whole prompt, while a detached job shows the snapshot's task preview, capped by the producer at 80 characters (the cap is the snapshot's, not the pane's). The task header also carries the job's latest agent activity line (the greatest-timestamp entry across its agents, through the same timestamped renderer and tool-noise filter as agent panes), so what the job is doing right now is visible without drilling into an agent row. For a round selection, a summary with one line per child. Selection follows a blocking or a detached agent alike; detached detail streams through the per-task `onUpdate` wiring in the subagent extension's `runDetachedJob`.
- **Thinking view:** an agent's reasoning surfaces two ways, both free of model-context cost and runtime files. While the agent runs, the detail pane renders a `thinking · live` section below the activity log: full-text thinking blocks (not the activity log's 60-character one-liners) styled like the main TUI's visible thinking (`thinkingText` color, italic), refreshed at the same ~3× a second poll. The live buffer is bounded per agent (the most recent ~20 blocks within ~64 KB, oldest evicted first) and lives only in the dispatch process's memory. After an agent finishes, `t` on its row streams its complete, uncapped thinking from the current session transcript: the press itself never reads the file synchronously, it renders a `reading transcript…` note under the transcript label while the parent session's `.jsonl` is streamed line by line in the background (readline over a read stream, capped at the file's open-time byte length so records appended mid-read never compete), so a multi-megabyte session neither blocks the view for the read's length nor is allocated as one string; the streamed lookup matches the `subagent` toolResult whose per-slot results match the agent (the file is read, never written), preferring the last matching record in file order that holds a matching slot whose own message-timestamp span (the slot's first and last message timestamps) lies inside the selected run's window (the row's startedAt/finishedAt widened by a 2 second tolerance on each side), and within that record the matching slot whose span end lies closest to the run's finishedAt (last in file order on ties), so repeat dispatches of one agent name resolve each row to its own run's slot, including same-name slots inside one parallel record and earlier steps of a chain round, whose shared record timestamp (stamped at dispatch completion) never gates the match, and a same-name sibling finishing inside the tolerance too, whose span end in the measured corpus sits seconds from the row's finishedAt where the row's own sits milliseconds; when no slot's span qualifies, the lookup falls back to the session-latest matching record's last matching slot in file order, so a window miss resolves exactly as the no-window lookup does; when the read lands, the pane switches to a `full thinking · transcript · t to return` reading view that survives polls until `t` is pressed again or the cursor moves; pressing `t` mid-read toggles off and aborts the read, moving the cursor or closing the view aborts it, and an aborted read never lands, so a record can never appear under the row it was not opened for; a failed read renders the `session transcript unavailable` note, the same one shown when no session transcript is trackable. `t` ignores running agents. Detached dispatches persist an empty `subagent` toolResult in the parent transcript (no per-agent results inside it), so on a finished detached agent whose live buffer holds thinking the reading view shows a `no transcript record for this agent; showing live buffer` note and keeps the live thinking section beneath it (the buffer is that agent's only full-text record), and when the buffer is empty too it shows a plain `no transcript record for this agent`. A finished agent whose matching record exists but holds no thinking shows `this agent's transcript record holds no thinking` instead (`this agent's transcript record holds no thinking; showing live buffer` when the live buffer is non-empty); no note claims the thinking itself is gone. A torn trailing line from the still-appending transcript never blocks completed results.
- **Tool-noise filter:** the detail pane's default hides the file-reading tool calls (`read`, `grep`, `find`, `ls`) so thinking and assistant text lead the pane; `ctrl+t` and its alias `ctrl+o` flip between the hidden and shown states, matched through pi's `app.tree.filter` keybinding actions (so user remaps are honored) with the raw keys as fallback. The header line names the current state (`tools hidden` / `tools shown`). Unknown tool names, unnamed calls, text, and thinking always stay visible; toggling re-anchors the detail window on the newest output, since filtering reshapes the line list.
- **Keys (fixed in v1):** `↑`/`↓` move the cursor, `←`/`→` collapse/expand the selected task, round, or the Completed umbrella, `tab`/`shift+tab` jump to the next/previous task, `pgup`/`pgdn` page the detail pane, `home`/`end` jump to its first/last line, `ctrl+t`/`ctrl+o` toggle tool-noise visibility, `t` toggles the selected finished agent's transcript thinking view, `esc` or the open key closes. The scroll keys work in both regular and fullscreen (alt-screen) modes: pi's fullscreen viewport handler defers its scroll keys to a focused overlay, so the overlay hosting is what lets them through when pi runs full screen. The surface is strictly read-only: nothing in the view steers, aborts, or injects into a dispatch.
- **Detail-pane scrolling:** the pane follows the newest output by default. `pgup` releases the follow and pages up (keeping one line of context); while released the window holds its place as new output streams in, with a `↓ new · end to follow` line marking output still below the window (the line hides again once the window itself reaches the newest line, as after a terminal resize, which can grow the held window over the tail while the hold stays held), and the hold survives the activity log evicting old entries at its 50-line cap; while the tree pane overflows into its `+N more` clip, the window and the marker share the body budget one row short so the newest output and the marker stay visible. Paging back to the bottom (including paging down once a resize has parked the held window on the tail) or pressing `end` re-follows and clears the marker; moving the cursor to a different row re-anchors on that row's newest output. In fullscreen the mouse wheel scrolls the pane with the transcript's own acceleration (clamped per event, through the same scroll model as the paging keys); regular mode degrades to the keyboard path (the wheel goes to the terminal's own scrollback there).
- **Hosting:** the overlay floats above the transcript and the editor for the view's whole lifetime, so no transcript remnant, footer, or strip widget constrains the frame; the view owns the full terminal height while open (the body budget is the terminal minus its own header and hints lines), and closing it restores the editor and any ambient strip widget beneath.

### Task labels

Dispatch payloads carry no task-ID field, so the label is parsed from the prompt text: the first `EXT-N` or `EXT-N-M` fleet task reference when the prompt names one (first match wins on multi-reference prompts), otherwise the prompt's first words truncated to 60 characters. A trailing eight-digit date segment is stripped from the capture, so a prompt citing its task file by path (`…/EXT-19-20261030-0918-….md`) labels its dispatch `EXT-19` instead of capturing the filename's date segment, which mimics the `EXT-N-M` child-id shape. Labels resolve at render time, and detached jobs resolve their task preview through the same heuristic on both surfaces.

### Hotkey configuration

Both extension hotkeys are configurable through the `subagentViewer` settings block in `settings.json`:

```json
{
  "subagentViewer": {
    "stripKey": "alt+s",
    "navigatorKey": "alt+n"
  }
}
```

When the block or a key is absent, the hardcoded defaults apply (`alt+s` strip, `alt+n` navigator; both unused by pi's built-in keybindings). pi's native `keybindings.json` cannot rebind extension shortcuts, and extension settings are read when the shortcuts register, so a changed key takes effect after `/reload` (or a new session). The in-view navigation keys are fixed and not configurable; the tool-noise toggle additionally honors pi's `app.tree.filter.noTools` and `app.tree.filter.cycleForward` remaps.
